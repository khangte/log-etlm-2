# 로그 생성기

- 상태: 완료 (기존 생성 기능·처리지연 측정·[측정 오버헤드 축소](#측정-오버헤드-축소-2026-11-19) 검증 완료. 아래 [검증 결과](#검증-결과))
- 적용 범위: 제품 v1 / 1단계 로그 생성기
- 사용자 지정 기준: 기본 5,000 EPS, 정상 주문 로그는 대략 1,000B 규모의 참고값, 직렬화된 로그 생성
- 데이터 원칙: 이름·이메일·상세 주소·IP 없이 합성 사용자 ID 사용
- 실행 설정은 `.env` 또는 환경변수에 명시하며 코드 기본값은 두지 않는다. 개발용 예시값은 `.env.example`에서 관리한다.

## 목표와 범위

외부 서비스 없이 주문 완료 이벤트와 필터링·오류 처리 검증용 로그를 생성한다. [개발환경](00-development-environment.md)에 따라 Python 3.12와 uv를 사용한다.

1단계는 생성, UTF-8 JSON 직렬화, 표준 출력·파일 저장, 로컬 검증까지 다룬다. Kafka 전송은 2단계에서 구현하며 생성기의 직렬화 결과를 메시지 값으로 그대로 사용한다. ClickHouse 저장 스키마와 평탄화 방식은 후속 단계에서 정의한다.

버스트 트래픽, 지연 이벤트, 중복 이벤트 주입은 이번 단계에서 제외한다. 정상 주문, health_check, 세 가지 불량 유형부터 검증한다.

## 데이터 최소화와 합성 데이터 원칙

- 사용자 식별은 합성 `context.user_id`로 한다. 실제 회원 정보나 실제 회원 ID를 입력받거나 연결하지 않는다. `session_id`와 주문 ID도 합성값만 사용한다.
- 이름, 이메일, 전화번호, 상세 주소, IP 주소는 스키마와 출력에서 제외한다. 마스킹된 개인정보도 생성하지 않는다.
- 국가·지역·도시, 기기와 유입 정보는 집계 검증용 합성값으로만 생성한다. 실제 사용자의 위치나 접속 정보를 수집하지 않는다.
- 페이지 경로에는 이름·이메일·사용자 식별자 등의 개인정보를 포함하지 않는다. 초기에는 쿼리 문자열 없는 고정 경로를 사용한다.
- Faker로 개인정보 형태의 필드를 채우지 않는다. 상태·오류 로그에도 외부 개인정보를 입력하거나 기록하지 않는다.
- 실제 서비스의 회원 테이블을 연결하는 기능은 이번 범위에 포함하지 않는다. 향후 실제 데이터 연계 시에는 ID 전환만으로 익명화가 보장된다고 가정하지 않고 별도 요구사항을 정의한다.

## 처리량과 로그 크기

| 항목 | 기준 |
| --- | --- |
| 처리량 단위 | EPS(Events Per Second), 초당 로그 건수 |
| 기본 목표 | 전체 로그 합계 5,000 EPS. 정상·health_check·불량 로그 모두 포함 |
| 로그 크기 | 정상 주문은 대략 1,000B 규모를 참고하되 최소·최대·고정 크기 조건은 두지 않음. 필드 값과 이벤트 종류에 따라 달라짐 |
| 직렬화 형식 | JSON 객체를 공백·들여쓰기 없는 한 줄로 직렬화하고 UTF-8 바이트로 인코딩. 한글은 유니코드 이스케이프 대신 UTF-8로 인코딩 |
| 크기 계산 | `len(payload_bytes)`로 실측. 객체 크기나 문자열 글자 수로 계산하지 않음 |
| 구분자 | stdout·파일은 페이로드 뒤에 LF 1바이트 추가. LF는 페이로드 크기와 별도 집계 |
| 원시 데이터량 | 실제 페이로드 바이트 합계 / 경과 시간으로 측정. 평균 1,000B라고 가정할 때 5,000 EPS는 약 5MB/s이며 실제 값은 이벤트 구성에 따라 달라짐 |

생성 단계의 결과는 딕셔너리가 아닌 직렬화된 `bytes`다. 출력 단계는 이를 다시 JSON으로 직렬화하거나 문자열로 감싸지 않는다. 불량 JSON도 UTF-8 바이트로 생성하되 의도적으로 JSON 파싱에 실패하도록 만든다.

크기를 맞추기 위한 필드나 패딩은 추가하지 않는다. 1,000B를 넘거나 미달해도 크기만으로 오류 처리하거나 필드를 자르지 않는다. health_check와 불량 로그도 각 구조에 따른 자연스러운 크기로 생성한다.

## 이벤트 구성과 비율

| 구분 | 기본 비율 | 5,000 EPS 기준 기대 건수 | 동작 |
| --- | --- | --- | --- |
| 정상 주문 | 85% | 4,250건/s | `event_name=order_completed`, 모든 주문 제약 충족 |
| 필터링 검증 | 10% | 500건/s | `event_name=health_check`, 유효한 JSON이지만 주문 분석에서 제외 |
| 불량 주문 | 5% | 250건/s | `order_completed` 기반으로 아래 오류 중 하나만 주입 |

- 각 이벤트의 유형을 설정된 비율에 따라 무작위 선택한다. 위 건수는 기대값이며 매초 정확한 건수를 보장하지 않는다.
- 비율의 합은 100%이며 각 값은 0~100% 범위다. 잘못된 설정은 생성 전에 거부한다.
- 불량 유형은 JSON 문법 오류, `properties.order_id` 누락, `properties.total_amount` 타입 오류를 기본적으로 같은 확률로 선택한다.
- JSON 문법 오류는 최종 JSON의 닫는 중괄호를 `!`로 교체한다. UTF-8 유효성·바이트 길이·한 줄 구조를 유지한다.
- 필드 누락 유형은 `order_id` 키를 제거한다. 타입 오류 유형은 `total_amount`를 문자열 `"invalid_amount"`로 바꾼다. 두 유형은 JSON 문법 자체는 유효해야 한다.
- 오류 유형은 페이로드에 별도 필드로 표시하지 않고 생성 통계에서 집계한다. 의도한 오류 외의 스키마·금액 오류는 만들지 않는다.

## 스키마와 추천 기본값

기존 중첩 구조인 `context`, `properties`, `properties.items`를 유지한다. 제품 v1의 분석 이벤트는 `order_completed` 하나이며 `event_type=view/click/purchase` 형태의 별도 스키마는 사용하지 않는다. 제품 버전과 `schema_version`은 별개다. 초기 계약은 `1.0.0`으로 제안한다.

정상 주문의 아래 필드는 모두 필수이며 `null`을 허용하지 않는다.

| 필드 | 타입·제약 | 추천 기본값 또는 생성 규칙 |
| --- | --- | --- |
| `event_id` | string, UUIDv4 | 이벤트마다 새 UUID 생성 |
| `event_timestamp` | string, ISO 8601 | 생성 시점의 UTC 시각, 밀리초 고정, `2026-11-16T06:08:00.123Z` 형식 |
| `event_name` | string | 정상·불량 주문은 `order_completed`, 필터링용은 `health_check` |
| `schema_version` | string | `1.0.0` |
| `context.user_id` | string | 실제 회원과 무관한 합성 ID. 사용자 풀에서 균등 선택, `usr_` + 5자리 이상 번호 |
| `context.session_id` | string | 이벤트마다 `sess_` + UUID의 32자리 16진수. 실제 사용자 세션 연속성은 모사하지 않음 |
| `context.is_logged_in` | boolean | `true` |
| `context.user_tier` | string, enum | `STANDARD`, `VIP` 중 등급 풀 가중치로 선택 |
| `context.device.os` | string | `iOS` |
| `context.device.os_version` | string | `18.1.1` |
| `context.device.app_version` | string | `4.12.0` |
| `context.device.device_model` | string | `iPhone16,1` |
| `context.device.device_type` | string | `mobile` |
| `context.network.carrier` | string | `synthetic` |
| `context.network.country` | string | `KR` |
| `context.network.region` | string | 지역 풀에서 가중치 선택 |
| `context.network.city` | string | 선택한 지역에 대응하는 합성 도시·구 값 |
| `context.page.current_url` | string | `/checkout/complete` |
| `context.page.referrer_url` | string | `/cart` |
| `context.page.utm_source` | string | `direct` |
| `context.page.utm_medium` | string | `none` |
| `properties.order_id` | string | `ord_` + 해당 이벤트의 UUID 32자리 16진수 |
| `properties.payment_method` | string, enum | `credit_card`, `kakao_pay`, `naver_pay`, `bank_transfer` 중 결제수단 풀 가중치로 선택 |
| `properties.currency` | string | `KRW` |
| `properties.total_amount` | integer, 0 이상 | `sum(item.price * item.quantity) - discount_amount` |
| `properties.discount_amount` | integer, 0 이상 | 상품 합계에 할인율 풀에서 균등 선택한 비율을 적용 |
| `properties.items` | array, 원소 1개 | 초기 검증을 단순하게 유지하기 위해 주문당 상품 1종으로 고정. 수량은 별도 선택 |
| `properties.items[].product_id` | string | 상품 풀에서 가중치 선택, `prod_` + 4자리 번호 |
| `properties.items[].product_name` | string | 상품 풀에 정의한 고정 이름 |
| `properties.items[].category` | string | 상품 풀에 정의한 `electronics`, `fashion`, `home` 중 하나 |
| `properties.items[].price` | integer, 양수 | 상품 풀의 고정 가격, 단위 KRW |
| `properties.items[].quantity` | integer, 양수 | 수량 풀에서 균등 선택 |

동일 상품 ID의 이름·카테고리·가격은 실행 중 바뀌지 않는다. 상품 풀은 시작 시 구성한다. 기기·유입 정보는 초기에는 위 합성값으로 고정하고 사용자·지역·상품·결제수단·수량·할인·등급을 변화시켜 집계 검증에 사용한다. 기기 버전 값은 합성 데이터이며 실행 환경의 버전 요구사항이 아니다.

`health_check`는 공통 필드 `event_id`, `event_timestamp`, `event_name`, `schema_version`만 포함하며 `context`, `properties`는 생략한다. 후속 처리에서는 `event_name`으로 먼저 분류한 뒤 주문 스키마를 검증한다.

### 데이터 계약

위 스키마는 `contracts/`의 JSON Schema(draft 2020-12)로 고정한다. 생성기 테스트와 후속 Spark 검증은 이 파일과 표준 샘플을 기준으로 한다. 스키마 변경 시 `schema_version`과 이 표, 계약 파일, 샘플을 함께 갱신한다.

- `contracts/schemas/order_completed.1.0.0.schema.json`, `contracts/schemas/health_check.1.0.0.schema.json`
- `contracts/samples/`: 정상 주문, health_check, 불량 3종의 표준 샘플. 실제 출력과 같은 한 줄 직렬화 형식이다.
- 정의 외 필드는 허용하지 않는다(`additionalProperties: false`). 개인정보 필드 유입을 계약 단계에서 막기 위함이다.
- JSON Schema로 표현하지 않는 규칙: `total_amount = sum(price × quantity) - discount_amount`, 상품 ID별 이름·카테고리·가격 일치, 지역·도시 조합. 이 규칙은 생성기 테스트와 스트림 처리 검증에서 확인한다.
- 기기·유입 정보 고정값, 풀 값·가중치 같은 생성 규칙은 계약이 아닌 생성기 기본값이므로 스키마는 타입·형식·열거값만 제한한다.

### 풀 정의

풀의 값·가중치는 코드가 기준이며 이 문서에 복제하지 않는다. 사용자·상품·지역·결제수단·회원 등급·이벤트 종류·불량 유형·수량·할인율 풀과 사용자 풀 생성 함수는 `apps/log_generator/src/log_generator/pools.py`에서 관리한다. 상품·지역 데이터 구조인 `Product`, `Location`도 같은 파일에 둔다.

- 외부 데이터 조회나 Faker는 사용하지 않는다. 가중치는 실제 통계가 아닌 검증용 합성 분포이며 각 풀의 가중치 합은 100이다.
- 선택은 호출자가 전달하는 `random.Random`의 `choice` 또는 `choices`를 사용한다.
- 사용자 풀은 양의 정수 크기를 받아 시작 시 한 번 만들고 이벤트마다 재사용하며 균등 선택한다.
- 회원 등급은 이벤트별 선택이며 사용자별 고정 등급은 보장하지 않는다.
- 상품의 ID·이름·카테고리·가격, 지역의 국가·지역·도시는 한 묶음으로 선택해 실행 중·실행 간 동일하게 유지하고 서로 다른 묶음의 값이 섞이지 않게 한다.
- 지역 값은 실제 사용자의 주소나 위치와 연결하지 않는다.
- 이벤트 종류와 불량 유형 비율은 위 [이벤트 구성과 비율](#이벤트-구성과-비율)을 따르며 코드 값과 일치해야 한다.

풀 검증에서는 사용자 ID 고유성·크기(크기 입력 검증은 설정 단계 `PRODUCER_USER_POOL_SIZE`에서 한 번만 한다), 상품 속성·가중치, 지역 조합과 seed에 따른 선택 재현성을 확인한다. 전체 생성기의 EPS 성능 검증과 구분한다.

## 실행과 출력

모듈 구성 (`apps/log_generator/src/log_generator/`):

- `config.py`: 프로젝트 루트 `.env`와 `PRODUCER_*` 환경변수를 읽어 타입 변환·검증을 적용한 `Config`를 만든다. 코드에는 환경변수 기본값을 두지 않는다.
- `generator.py`: 정상 주문·health_check·불량 주문을 직렬화된 `bytes`로 생성한다. 불량 유형별 강제 생성 경로(`invalid_order`)를 둔다.
- `outputs/file.py`: 기존 파일을 덮어쓰지 않는 파일 출력 연결을 담당한다.
- `main.py`: 실행 진입점(`uv run log-generator`). 속도 제어, stdout·file 출력, 통계를 담당한다. Kafka 전송 모드는 2단계에서 추가한다.
- 종료 코드: 0 정상 완료, 1 출력 오류, 2 설정 오류, 130 Ctrl+C.
- 속도 제어: 5ms 틱마다 누적 목표 대비 부족분만 출력한다. 한 틱 허용량의 2배를 넘게 밀리면 밀린 분량을 포기하고 기준 시각을 당긴다. 목표 EPS 유지는 단위 테스트(1,000 EPS로 500건 출력 시 경과 0.45~0.6초)로 검증한다. 부하 프로파일 실행 시 구간 전환마다 누적 기준을 다시 잡는다([시간대별 부하 프로파일](06-load-profile.md#속도-제어)).

| 설정 | `.env.example` 예시값 | 규칙 |
| --- | --- | --- |
| `eps` (`PRODUCER_EPS`) | `5000` | 양의 정수, 생성부터 출력까지 완료한 전체 로그 기준 |
| `output` (`PRODUCER_OUTPUT`, `PRODUCER_OUTPUT_PATH`) | `stdout` | `stdout`, `file` 중 선택. `file`은 경로 필수 |
| `max_events` (`PRODUCER_MAX_EVENTS`) | `300000` | 0 이상 정수. 기본 목표 속도에서 약 60초. `0`은 무제한 |
| `user_pool_size` (`PRODUCER_USER_POOL_SIZE`) | `500` | 양의 정수. 시작 시 사용자 풀 구성 |
| `profile` (`PRODUCER_LOAD_PROFILE`) | 빈 값 | 부하 프로파일 CSV 경로. 빈 값이면 `eps` 고정 속도. 형식·검증은 [시간대별 부하 프로파일](06-load-profile.md#생성기-요구사항) |
| 상품 풀 | `pools.py` 고정 목록 | 임의 크기 확장은 후속 요구사항으로 정의 |
| `seed` (`PRODUCER_SEED`) | 미지정 | 지정 시 이벤트 유형·상품 등 무작위 선택 재현. UUID와 현재 시각을 포함한 전체 바이트 재현은 보장하지 않음 |
| 상태 출력 주기 (`PRODUCER_STATUS_INTERVAL_SEC`) | 1초 | 데이터와 분리해 stderr에 JSON 한 줄로 출력. 출력 지연으로 주기가 밀리면 밀린 횟수만큼 몰아서 출력하지 않고 현재 시각부터 다시 센다 |

- 기본 실행 `uv run log-generator`에서 `python-dotenv`로 프로젝트 루트 `.env`를 자동으로 읽는다. 실행 디렉터리와 무관하게 소스 위치 기준으로 루트를 찾는다. 설정 우선순위는 이미 설정된 환경변수 > `.env`이며 코드 기본값은 없다. `.env.example`은 템플릿일 뿐 실행 시 읽지 않는다. `.env`가 없으면 환경변수만 사용한다(컨테이너는 Compose가 주입). 소스 위치가 얕아 루트를 계산할 수 없는 설치 경로(예: 컨테이너 `/app/src/log_generator`)에서도 import가 실패하지 않고 환경변수만 사용한다.
- 모든 `PRODUCER_*` 설정 키를 명시해야 한다. 누락 시 시작 전에 설정 오류(종료 코드 2)로 종료한다. EPS·출력 대상·최대 건수·사용자 풀 크기·상태 주기는 빈 값도 거부한다.
- `PRODUCER_SEED=`는 무작위 seed 미지정을 명시한다. `PRODUCER_OUTPUT_PATH=`는 stdout 모드에서만 허용하며 file 모드에서는 경로가 필수다. 이 두 키도 생략할 수 없다.
- 두 설정 파일이 모두 없어도 필요한 모든 키를 환경변수로 제공하면 실행할 수 있다. 별도 CLI 옵션·YAML 로더·Kafka 라이브러리는 이번 단계에서 추가하지 않는다.
- `PRODUCER_MAX_EVENTS=0`은 무제한 실행이다. 값의 형식·범위 오류는 생성 전에 거부한다(종료 코드 2).
- stdout·파일에는 직렬화된 페이로드와 LF만 출력한다. 불량 JSON도 한 줄씩 기록하므로 파일의 모든 줄이 유효한 JSON이라고 가정하지 않는다.
- 파일은 명시된 경로에 새로 생성한다. 기존 파일이 있으면 덮어쓰지 않고 오류로 종료한다. 자동 회전·압축은 이번 단계에서 제외한다.
- 속도 제어는 단조 증가 시계를 사용하고 짧은 주기로 분산 출력한다. 1초 분량을 한꺼번에 내보내는 방식은 피한다. 지연을 따라잡기 위해 무제한으로 몰아서 출력하지 않는다.
- 출력 지연 시 추가 생성을 늦추고 실제 EPS 하락을 기록한다. 이벤트를 조용히 버리거나 메모리 대기열을 무제한으로 늘리지 않는다.
- 출력 오류는 stderr에 기록하고 비정상 종료한다. `max_events` 도달 또는 Ctrl+C 시 출력 버퍼를 비우고 최종 통계를 기록한다. 출력 오류로 기록하지 못한 건은 성공 건수에 포함하지 않는다. 단, 출력 완료는 출력 버퍼에 쓴 기준이므로 출력 오류로 종료하면 버퍼에 남아 있던 건(파일 최대 1MB, stdout 약 8KB 분량)이 실제 기록량보다 많게 집계될 수 있다. 정상 완료·Ctrl+C는 버퍼를 비운 뒤 집계하므로 일치한다.
- 통계에는 목표·실제 EPS, 출력 완료 건수·페이로드 바이트 수, 실제 B/s, 페이로드 평균·최대 크기, 이벤트 유형별 건수, 불량 유형별 건수, 경과 시간과 오류 건수를 포함한다. 출력 완료는 출력 버퍼에 기록한 기준이며 디스크 영속화를 보장하는 의미는 아니다.

## 처리지연 측정

후속 단계에서도 아래 공통 원칙을 따른다.

범위 축소(2026-11-19): 파이프라인은 Kafka 출력 모드만 사용하므로 v1은 생성·직렬화 시간만 측정한다. stdout·파일 출력 호출 시간은 v1 범위에서 제외한다. 이 두 모드는 단독 검증·디버깅용이며 지연 경로에 들어가지 않는다. Kafka 출력의 전송 지연은 [Kafka PRD](02-kafka-ingestion.md)의 ACK 지연·생성 → Kafka 지연이 맡는다.

### 공통 측정 원칙

- 서비스 사이의 시각 비교는 UTC 기준으로 하며 호스트 시계를 동기화한다. 저장 시각은 밀리초 이상의 정밀도를 사용하되 기존 `event_timestamp`의 밀리초 형식은 유지한다. 시계 차이로 음수 지연이 나오면 0으로 숨기지 않고 측정 이상으로 집계한다.
- 같은 프로세스 안의 소요시간은 `perf_counter_ns()` 같은 단조 증가 시계의 차이로 측정한다. 서로 다른 프로세스의 단조 증가 시계 값은 비교하지 않는다.
- 단계 내부 처리시간과 단계 사이 대기·전달 지연을 구분한다. 서로 겹치는 구간을 합산해 종단 간 지연으로 표시하지 않는다.
- 지표에는 측정 구간, 단위(ms), 건수, 실패 건수와 평균·p50·p95·p99를 기록한다. 집계 구간과 샘플링 여부를 명시하며 구간별 백분위수를 단순 평균하지 않는다. 지연 목표값은 각 단계 착수 시 확정한다.
- 원본 JSON에 측정용 필드를 추가하거나 기존 시각을 덮어쓰지 않는다. Kafka 메타데이터, 후속 저장 컬럼, 별도 운영 지표를 사용한다. `event_id`, 배치 ID 등은 상관관계 확인용이며 시계열 지표의 개별 라벨로 사용하지 않는다.
- 재시도는 시도별 소요시간·실패와 최종 성공까지의 시간을 구분한다. 종단 간 지연은 최초 생성 시각을 유지한다. 정상 주문·health_check·불량 로그의 처리 경로와 측정 건수를 구분한다.

### 생성기 측정 위치

| 측정 항목 | 시작 | 종료 | 의미 |
| --- | --- | --- | --- |
| 생성·직렬화 시간 | 이벤트 생성 호출 직전 | 최종 UTF-8 바이트 반환 직후 | 필드 선택·객체 구성·직렬화·불량 주입을 포함하며 속도 제어 대기는 제외 |
| 출력 호출 시간(v1 범위 제외) | stdout·파일 쓰기 직전 | 쓰기 호출 반환 직후 | 출력 버퍼에 기록하는 데 걸린 시간. 디스크 영속화 시간이 아님 |

- 기존 `event_timestamp`는 이벤트 생성 시점이며 종단 간 지연의 기준이다. 생성·직렬화 시간은 별도 단조 증가 시계로 측정한다.
- 이벤트별 측정값을 stdout 페이로드에 섞지 않고 상태 지표로 집계한다. flush 소요시간은 개별 쓰기와 분리한다.
- Kafka 전송 측정은 [Kafka PRD](02-kafka-ingestion.md)에 따른다.
- 4단계부터 Kafka 출력 모드의 생성·직렬화 시간과 Producer 지표를 1초 구간 통계로 ClickHouse `ops.producer_stats`에 기록한다. 방식과 실패 정책은 [ClickHouse 운영 지표 저장](04-clickhouse-storage.md#운영-지표-저장)을 따른다.

## 측정 오버헤드 축소 (2026-11-19)

부하 프로파일 상한 확인 1차 측정에서 단일 생성기는 10,000 EPS 목표에 못 미쳤다(9,359 EPS, 프로세스 CPU 평균 0.91코어). 원인은 프로세스 CPU 포화였다([부하 프로파일 PRD](06-load-profile.md)). 그래서 서버 로직이 아닌 측정용 처리 비용을 줄인다.

### 원칙

- 생성기는 실무의 앱 서버를 대신한다. 이벤트 조립(dict 구성, `uuid4`, 현재 UTC 시각)과 표준 `json` 직렬화는 서버 로직 모사이므로 성능을 이유로 우회하지 않는다. 템플릿 직렬화, UUID 생성 방식 변경 같은 최적화는 하지 않는다.
- 줄이는 대상은 실제 서버에는 없는 측정용 처리다. 지표의 의미·단위·집계 방식은 바꾸지 않는다.
- 튜닝 순서: 단일 생성기 기준으로 Producer → Kafka → Spark를 먼저 튜닝한다. 그다음 생성기를 2개 프로세스로 확장한다. 확장 단계의 방식과 판정은 그때 [부하 프로파일 PRD](06-load-profile.md)에 정한다.
- Producer 설정(`linger.ms`, `batch.size`, `compression.type`) 튜닝은 이 작업이 끝난 뒤 별도로 진행한다.

### 변경 대상

| 대상 | 현재 | 변경 | 근거 |
| --- | --- | --- | --- |
| 생성 → Kafka 지연의 `event_timestamp` 취득 | delivery 콜백마다 메시지 값 전체를 `json.loads`로 다시 파싱(건당 약 7.9µs, 단독 실행 기준 메인 스레드 건당 비용의 약 17%) | 생성기가 이벤트를 만들 때 가진 `event_timestamp` 문자열을 전송 시 delivery 콜백에 함께 넘긴다 | 실제 서버도 ACK 콜백에서 보낸 payload를 다시 파싱하지 않는다. [Kafka PRD](02-kafka-ingestion.md#처리지연-측정) "콜백 시점에 이미 가진 원본 `event_timestamp`"와 같은 의미다 |
| 생성·직렬화 시간 계측 | 이벤트마다 `perf_counter_ns()` 2회와 히스토그램 1회 갱신 | 유지 | 완료 기준 10이 측정 건수 = 생성 건수를 요구한다. 건당 비용도 작다 |

- 넘기는 값은 메시지 값에 들어간 `event_timestamp` 문자열 그 자체다. 콜백은 기존과 같은 방식(`datetime.fromisoformat` 후 epoch ms)으로 변환하므로 지연 값이 변경 전과 같다.
- 불량 유형 `malformed_json`은 지금처럼 "해석 불가"로 집계한다(시각을 넘기지 않음). 기존에는 JSON 파싱 실패로 이렇게 집계됐다. 바뀐 뒤에도 해석 불가 건수 = 불량 JSON 건수가 유지되어 [ClickHouse PRD](04-clickhouse-storage.md)의 `gen_to_kafka_ms_count < acked` 관계가 같다. `missing_order_id`·`invalid_amount_type`은 `event_timestamp`가 있으므로 지금처럼 집계한다.
- 원본 메시지 값(bytes)·key·헤더는 바꾸지 않는다.

## 검증 및 완료 기준

1. **독립 실행:** Kafka 등 외부 서비스 없이 stdout·파일 모드가 동작하고 설정 오류와 기존 파일 충돌을 생성 전에 거부한다.
2. **크기·직렬화:** 정상·health_check·불량 세 유형을 각각 생성해 최종 UTF-8 바이트 크기와 이벤트 유형별 평균·최대 크기를 측정한다. 크기 맞춤용 필드가 없고 값의 길이가 달라도 정상 생성되는지 확인한다. 한글 상품명 사례에서도 글자 수 대신 바이트 수로 계산한다. LF는 별도 1바이트이며 이중 직렬화가 없어야 한다.
3. **스키마·금액:** 정상 주문의 필수 필드, 타입, UUID, UTC 시각, 풀 범위, 상품 일관성과 주문 금액 계산을 검증한다. health_check는 주문 필드 없이 유효한 JSON이어야 한다.
4. **불량 주입:** JSON 문법 오류만 파싱에 실패하고 누락·타입 오류는 JSON 파싱 후 해당 주문 검증에 실패해야 한다. 세 오류를 각각 강제로 생성하는 검증 경로를 둔다.
5. **비율:** 고정 seed로 300,000건을 생성해 85%·10%·5% 각각의 오차가 ±0.5%p 이내인지 확인한다. 불량 집합 내 세 유형의 비율은 각각 1/3 대비 ±2%p 이내여야 한다.
6. **성능:** 단일 프로세스, 파일 출력, 기본 스키마·풀·이벤트 비율로 5초 준비 실행 후 별도 60초 측정한다. 측정 시 건수 제한은 해제한다. 측정 구간의 출력 완료 건수 / 실제 경과 시간으로 계산한 평균이 5,000 EPS 대비 ±5% 이내여야 한다. 터미널 렌더링 속도는 성능 기준에서 제외하고 준비 구간의 건수·시간도 측정에서 제외한다.
7. **자원·종료:** 성능 검증에서 CPU, 최대 RSS, 출력 파일 크기, 실제 페이로드 평균·최대 크기·B/s와 실행 환경을 기록한다. 건수 제한·Ctrl+C에서 최종 집계와 출력 건수가 일치하고 출력 실패 시 비정상 종료와 오류 통계를 확인한다.
8. **환경 설정:** `.env` 자동 로딩, `.env` 부재·루트 계산 불가 시 환경변수 전용 실행, 실행 디렉터리 독립성, 환경변수 우선순위, 모든 설정 키 누락·필수값 공백 거부, 명시적인 빈 seed·stdout 경로를 검증한다. 테스트용 매핑을 전달할 때는 실제 `.env`를 읽지 않는다.
9. **데이터 최소화:** 스키마·생성 결과에 이름·이메일·전화번호·상세 주소·IP 필드가 없고, 사용자·세션·주문 ID가 합성값인지 확인한다. 경로는 쿼리 문자열 없는 고정값이며 지역·기기 정보에 실제 사용자 데이터를 사용하지 않는다.

10. **처리지연 측정(범위 축소, 2026-11-19):** Kafka 출력 모드에서 생성·직렬화 시간이 1초 구간마다 `ops.producer_stats`에 기록되고, 측정 건수가 생성 건수와 같은지 확인한다. 측정 활성화 상태에서 기존 처리량 기준을 충족해야 한다. 원본 계약과 출력 바이트 구조가 유지되어야 한다. 출력 호출 시간과 출력 지연 주입 검증은 v1 범위에서 제외한다.

11. **측정 오버헤드 축소(2026-11-19):** 다음을 모두 확인한다.
    - 메시지 값 bytes, 이벤트 비율, 고정 seed 선택 결과가 변경 전과 같다. 기존 단위 테스트를 통과해야 한다.
    - 같은 이벤트 열에 대해 생성 → Kafka 지연 히스토그램, 해석 불가 건수, LogAppendTime 아님 건수가 변경 전 방식과 같다. 해석 불가 건수는 `malformed_json` 건수와 같다.
    - 메인 스레드의 건당 비용(생성·직렬화 + 큐 등록 + delivery 콜백 처리)을 변경 전후 같은 방법으로 측정해 기록한다.
    - 단일 생성기로 상한 확인 프로파일(`spike-10k.csv`)을 전체 스택과 함께 실행해 ceiling 구간 EPS와 프로세스 CPU를 1차 측정(9,359 EPS, 0.91코어)과 비교한다. 이 값은 정책 결정용 참고값이며 통과 조건이 아니다.

검증 결과에는 목표 EPS와 실측 EPS를 구분한다. 성능 기준에 미달하면 원인과 실측치를 기록하고 완료로 처리하지 않는다.
