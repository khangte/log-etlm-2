# 시간대별 부하 프로파일

- 상태: 구현 중 (완료 기준 1~6 완료. 2026-11-23 단일 생성기 튜닝 후 평시·지속 용량 충족, 생성기 2개로 [spike 통과](03-stream-processing.md#스파이크-판정-생성기-2개-2026-11-23)·[step 지속 용량 12,000 EPS](03-stream-processing.md#지속-용량-판정-생성기-2개-step-재측정-2026-11-23). 완료 기준 7(`daily.csv` 전체 확인) 전)
- 적용 범위: 제품 v1 (6단계 상세 세팅 조정의 부하 모델·튜닝 목표·측정 부하)

## 목표

부하 모델(평시·평시 피크·지속 용량·스파이크)과 상황별 튜닝 목표를 정한다. 각 목표를 판정하는 프로파일로 생성기를 실행해 Producer → Kafka → Spark 순으로 튜닝하고, 결과를 같은 기준으로 비교한다.

- 판정은 배치 하나하나가 아니라 상황별 목표로 한다. 평시에는 트리거 주기 안에 여유를 두고 처리한다. 스파이크에는 지연과 누적을 허용하고 회복 시간으로 판정한다.
- 튜닝 순서: 단일 생성기 기준으로 Producer → Kafka → Spark를 튜닝한다. 그다음 생성기를 2개 프로세스로 확장해 단일 생성기가 낼 수 없는 부하(11,000 EPS 이상)를 판정한다.

## 범위

- 범위: 부하 모델과 튜닝 목표, 프로파일 파일, 생성기의 부하 프로파일 실행(설정·속도 제어·상태 출력·운영 지표의 목표 EPS), 프로파일별 측정과 판정.
- 튜닝 변경 자체(설정값·코드)는 해당 단계 PRD([로그 생성기](01-log-generator.md)·[Kafka](02-kafka-ingestion.md)·[Spark](03-stream-processing.md)·[ClickHouse](04-clickhouse-storage.md))에 기록한다. 컨테이너 자원 상한 변경은 이 문서의 [자원 조정](#자원-조정)에 기록한다.
- 제외: 구간 사이 선형 전환, 프로파일 반복 실행, 시뮬레이션 시각을 이벤트 시각에 반영, `ops.producer_stats` 스키마 변경, Grafana 구간 annotation.

## 부하 모델

평시 피크를 먼저 정하고, 지속 용량과 스파이크는 그 배수로 정한다.

| 구분 | EPS | 정의 |
| --- | ---: | --- |
| 평시 기준 | 5,000 | 프로젝트 기본 부하([로그 생성기](01-log-generator.md) 기본 5,000 EPS) |
| 평시 피크 | 7,500 | 평시 기준 × 1.5. 하루 중 가장 높은 정상 부하 |
| 지속 용량 목표 | 10,000 이상 | 평시 피크 × 1.33. 평시 피크 대비 처리 여력 33% |
| 스파이크 | 12,000 × 150초 | 평시 피크 × 1.6의 짧은 버스트. 지속 용량을 일부러 넘긴다 |

- 실무 기준: 평시 최대 부하의 1.25~1.5배를 처리할 수 있게 용량을 잡는다. 평시 최대 부하에서는 배치 처리시간이 트리거 주기의 70~80% 이하가 되게 한다. 이 문서는 70%(5초 트리거에서 3.5초)를 쓴다.
- 회복 시간 목표(60초)와 지속 용량 목표(10,000 EPS)는 같은 조건이다. 처리 용량을 C라고 하면 스파이크 150초 동안 (12,000 − C) × 150건이 쌓이고, 이후 5,000 EPS 구간에서 초당 (C − 5,000)건씩 줄어든다. C = 10,000이면 300,000건이 쌓이고 60초에 해소된다. C = 11,000이면 150,000건이 쌓이고 25초에 해소된다.
- Spark 입력 상한(`SPARK_MAX_OFFSETS_PER_TRIGGER` ÷ 트리거 주기)이 처리 용량의 상한이다. 현재 65,000 ÷ 5초 = 13,000 EPS다(2026-11-23 55,000에서 상향, [Spark B1](03-stream-processing.md#b1-배치-상한-65000-실험-2026-11-23)). 지속 용량을 이보다 높이려면 이 값도 함께 조정한다.

## 튜닝 목표

| 상황 | 판정 프로파일 | 목표 |
| --- | --- | --- |
| 평시 (≤ 7,500 EPS) | `steady.csv`, `daily.csv` | 1초 구간의 99% 이상에서 ACK p95 ≤ 100ms. 배치 트리거 시간 p99 ≤ 3,500ms. 종단 간 지연 p99 ≤ 10초. backlog 증가 추세 없음 |
| 지속 용량 | `step.csv` | 10,000 EPS 단계까지 통과. 개별 배치가 5초를 넘어도 되지만 단계 동안 backlog가 쌓이지 않는다 |
| 스파이크 | `spike.csv` | spike 구간 종료 후 60초 안에 backlog 0, Kafka → 콜백 p95가 warmup 구간 p95의 1.5배 이내로 회복. spike 중 지연은 기록만 한다 |
| 공통 | 모든 프로파일 | 생성 = ACK, 정상 주문 생성 건수 = `silver.order_events` 적재 건수(`event_id` 고유 수 포함). 쿼리·출력·ClickHouse 쓰기 실패 0건, Spark 재시작 0회 |

- 종단 간 지연은 `event_timestamp` → `silver.order_events.ingested_at`이다. 트리거 대기만으로 최대 5초가 들기 때문에 p99 10초 목표를 맞추려면 배치 처리시간을 줄여야 한다.
- 단일 생성기는 10,000 EPS까지 낼 수 있다(아래 현재 기준값). 단일 생성기 단계에서는 `step.csv`의 11,000·12,000 EPS 단계와 `spike.csv`를 참고값으로 기록한다. 이 둘은 2개 프로세스로 확장한 뒤 판정한다.

## 프로파일 정의

## 생성기 요구사항

### 설정

| 키 | `.env.example` 예시값 | 규칙 |
| --- | --- | --- |
| `PRODUCER_LOAD_PROFILE` | 빈 값 | 프로파일 CSV 경로. 빈 값이면 기존처럼 `PRODUCER_EPS` 고정 속도로 실행한다. 상대 경로는 프로젝트 루트 기준이다 |

- 키는 다른 `PRODUCER_*` 키처럼 반드시 명시한다. 빈 값을 허용하는 키로 추가한다.
- 프로파일을 지정하면 `PRODUCER_EPS`는 쓰지 않는다. 키 자체와 값 검증은 기존대로 유지한다.
- `PRODUCER_MAX_EVENTS`는 프로파일과 함께 적용한다. 프로파일 종료나 최대 건수 도달 중 먼저 오는 쪽에서 종료한다. 프로파일 측정은 `0`(무제한)으로 실행한다.
- 프로파일 파일 위치: `apps/log_generator/profiles/steady.csv`, `step.csv`, `spike.csv`, `daily.csv`. 2개 프로세스 실행용 파일은 `spike-half.csv`·`step-half.csv`다(2026-11-23). 각각 `spike.csv`·`step.csv`와 구간·길이·label이 같고 EPS만 절반이다(spike 2,500/6,000/2,500, step 2,500/4,000/4,500/5,000/5,500/6,000). 두 프로세스가 같은 파일로 동시에 실행하며, 판정은 원래 프로파일(`spike.csv`·`step.csv`) 구간 경계와 두 `run_id` 합계로 한다.

### 프로파일 파일 형식

```csv
duration_sec,eps,label
300,1500,00-02
```

- 첫 줄은 헤더 `duration_sec,eps,label`로 고정한다.
- `duration_sec`·`eps`는 양의 정수, `label`은 빈 값이 아닌 문자열이다.
- 다음 경우 생성 시작 전에 설정 오류(종료 코드 2)로 종료한다: 파일 없음·읽기 실패, 헤더 불일치, 열 개수 불일치, 정수 변환 실패, 1 미만 값, 빈 `label`, 데이터 행 0개.

### 속도 제어

- 구간 안에서는 기존 속도 제어(5ms 틱, 누적 목표 대비 부족분 출력, 한 틱 허용량 2배 초과 밀림 포기)를 그대로 쓴다.
- 구간 전환 시 누적 기준을 현재 시각·현재 출력 건수로 다시 잡고 새 EPS와 한 틱 허용량을 적용한다. 이전 구간의 부족분을 새 구간에서 몰아서 보내지 않는다.
- 구간 경계는 실행 시작 시각(monotonic) + 누적 `duration_sec`로 정한다. 출력 지연으로 경계를 넘긴 만큼 다음 구간이 짧아지며, 전체 실행 길이는 프로파일 합계를 유지한다.
- 마지막 구간이 끝나면 flush 후 `completed`로 종료한다.

### 이벤트 시각

- `event_timestamp`는 기존처럼 실제 생성 시각(UTC)이다. 시뮬레이션 시각을 쓰면 종단 간 지연 측정이 깨지므로 반영하지 않는다.

### 상태·통계·운영 지표

- 주기 상태 줄에 현재 구간의 `target_eps`와 `label`을 추가한다.
- 최종 통계의 `target_eps`는 프로파일 실행이면 프로파일 이름(파일 경로)과 구간 목록(`label`·`duration_sec`·`eps`)으로 대신 기록한다.
- 구간 전환 시 stderr에 전환 시각·이전/다음 `label`·EPS를 JSON 한 줄로 기록한다.
- `ops.producer_stats.target_eps`에는 1초 구간 시작 시점의 구간 EPS를 기록한다. 스키마는 바꾸지 않는다. 경계를 걸친 1초 행은 판정에서 제외한다.
- 파이프라인 운영 대시보드의 기존 Producer 패널(`목표`·`생성`·`ACK`)이 `target_eps`를 그대로 그리므로 Grafana 변경은 없다.

## 측정 방법

- 자원·설정은 `.env`·Compose 기본값 그대로다. Kafka UI는 끈다. Grafana 대시보드는 측정 중 열어 두지 않는다. 자동 새로고침 쿼리가 ClickHouse CPU를 쓰기 때문이다(2026-11-23 spike3 실행에서 `grafana_reader` 쿼리 CPU 188초, ClickHouse CPU 상한 걸린 주기 16.2%). 측정 중 코드·설정을 바꾸지 않는다.
- Spark는 측정마다 별도 체크포인트·`latest`로 시작한다. 생성기는 Spark 첫 배치 진행 로그 확인 후 시작한다.
- 각 프로파일 실행의 생성기 `run_id`와 Spark `run_id`를 기록한다.
- 구간 지표는 `ops.producer_stats`·`ops.spark_query_progress`·`silver.order_events`에서 구간 시각으로 잘라 집계한다. 측정 스크립트·결과 JSON은 `docs/measurements/`에 둔다.
- 측정 중 Kafka·Spark·ClickHouse 컨테이너 CPU·메모리를 함께 기록한다.
- WSL VM 정지 구간이 발생하면 [호스트 멈춤 기록](04-clickhouse-storage.md#호스트-멈춤-기록)으로 확인하고, 해당 구간은 v1 판정과 같은 방식으로 분리해 보고한다.

## 판정 기준

[튜닝 목표](#튜닝-목표)를 아래 방식으로 판정한다. 실행 시작 후 120초는 워밍업으로 제외한다. 구간 경계를 걸친 1초 행과 배치는 판정에서 제외한다. 결과는 구간별 표로 기록한다.

### 평시 (`steady.csv`, `daily.csv`)

구간마다 판정한다.

1. **생성·전송:** 구간 ACK EPS가 목표의 ±5% 이내이고, 구간 1초 행의 99% 이상에서 ACK p95가 100ms 이하다. 지연 SLO는 개별 구간이 아니라 비율로 판정한다(2026-11-19, 기준값 측정에서 300개 중 1개 초과로 실패한 뒤 변경).
2. **배치 시간:** 구간 배치의 트리거 시간(`trigger_execution_ms`) p99가 3,500ms 이하다.
3. **종단 간 지연:** 구간 이벤트의 p99가 10초 이하다. 10초 초과 건수를 기록한다.
4. **누적:** backlog(`latest_offsets` 합 − `end_offsets` 합)가 구간 동안 증가 추세가 아니고, 0이 아닌 backlog는 다음 배치에서 0으로 돌아온다.

### 지속 용량 (`step.csv`)

단계마다 판정한다. 첫 실패 단계부터는 기록만 한다.

1. **생성:** 단계 생성 EPS가 목표의 ±5% 이내다. 못 미치면 그 단계는 생성기 한계로 기록하고 판정하지 않는다.
2. **누적 없음:** 단계 마지막 60초의 backlog 최댓값이 그 단계 EPS × 트리거 주기(5초) 이하이고, 단계 동안 증가 추세가 아니다.
3. **결과:** 통과한 가장 높은 단계를 지속 용량으로 기록한다. 단계별 트리거 시간 평균·최대와 실처리량(입력 건수 ÷ 트리거 시간 합)을 함께 기록한다.

### 스파이크 (`spike.csv`)

1. **생성:** spike 구간 생성 EPS가 12,000의 ±5% 이내다. 2개 프로세스로 실행하면 두 `run_id`의 합계로 본다. 못 미치면 이후 기준은 참고값이다.
2. **누적:** spike 구간 backlog 최댓값과 spike 중 종단 간 지연 최댓값을 기록한다.
3. **회복:** spike 종료 시각부터 backlog 0과 Kafka → 콜백 p95 ≤ warmup p95 × 1.5를 함께 만족하는 첫 배치까지가 60초 이하다.

### 공통

1. **건수 대조:** 실행 전체에서 생성 = ACK, 정상 주문 생성 건수 = `silver.order_events` 적재 건수(`event_id` 고유 수 포함).
2. **오류:** 쿼리·출력·ClickHouse 쓰기 실패 0건, Spark 재시작 0회.
3. **자원:** 컨테이너별 CPU 상한에 걸린 주기 비율, 메모리 최대치(Spark는 `memory.stat`의 `anon`·`file` 포함), 생성기 프로세스 CPU를 기록한다.

기준을 못 넘긴 항목은 실패로 기록하고 원인 구간(생성기·Kafka·Spark·ClickHouse)을 [파이프라인 운영 대시보드](05-grafana-dashboard.md#파이프라인-운영-대시보드) 판정 순서로 지목한다.

## 완료 기준

1. **설정 검증:** 프로파일 형식 오류 각각이 시작 전 종료 코드 2로 거부된다(단위 테스트). 빈 `PRODUCER_LOAD_PROFILE`이면 기존 고정 속도 동작과 테스트가 그대로 통과한다.

8. **문서:** 프로파일 파일과 테스트가 이 문서의 정의와 일치한다. 튜닝 변경은 해당 단계 PRD에 기록한다.

- 비교한 대안:
  - Spark standalone(master·worker 분리): 단일 호스트에서는 처리량이 늘지 않는다. 같은 CPU를 프로세스 3개가 나누고, executor와 driver 사이 직렬화·네트워크 홉이 생긴다. 병렬도는 Kafka 파티션 3개가 상한이다. 노드를 늘려 수평 확장할 때 다시 검토한다.

  - Grafana 내장 플러그인 끄기: 메모리를 줄일 수 있지만 내장 데이터 소스에 적용되는지 확인하지 않았다. 상한을 올리는 쪽이 확실하다.
- 검증: 상한 확인 프로파일(`spike-10k.csv`)로 측정했다([1차](#상한-확인-프로파일-측정-1차-ceiling-10000-eps-생성기-1개-spark-cpu-4-2026-11-19), [2차](#상한-확인-프로파일-측정-2차-ceiling-10000-eps-생성기-2개-spark-cpu-4-2026-11-19)). 결과: Spark 50,000건 배치 트리거 5,986ms → 4,493ms(2차), 10,000 EPS 지속 처리.
