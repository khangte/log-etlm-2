# 시간대별 부하 프로파일

- 상태: 구현 중 (생성기 구현·완료 기준 1~3·5·6 완료. 스파이크 측정 1차는 생성 기준 미달, 2차(생성기 2개)·3차(배치 상한 55,000건) 통과. 상한 확인 측정 2차 통과. 일간 측정(완료 기준 4) 남음)
- 적용 범위: 제품 v1 (6단계 상세 세팅 조정의 측정 부하)

## 목표

고정 5,000 EPS 대신 하루 트래픽 모양을 압축한 변동 부하를 생성기로 보내고, 현재 설정의 파이프라인이 부하 구간별로 어디서 먼저 한계에 닿는지 측정한다. 이 측정 결과가 6단계 상세 세팅 조정의 출발점이다.

- 일간 프로파일: 구간별 정상 상태 처리 여부를 판정한다.
- 상한 확인 프로파일: 입력을 Spark 이론상 최대치(10,000 EPS)에 맞춰 그 속도를 지속 처리하는지 확인한다. 자원 조정 효과를 비교하는 용도다.
- 스파이크 프로파일: Spark 입력 상한을 일부러 넘겨 backlog 누적과 회복을 측정한다. 세팅을 바꿔 가며 반복 비교하는 용도다.

## 범위

- 범위: 생성기의 부하 프로파일 실행(설정·속도 제어·상태 출력·운영 지표의 목표 EPS), 프로파일 파일, 프로파일별 측정과 판정.
- 제외: 측정 후 조정은 [자원 조정](#자원-조정) 절에 정의한 것만 적용한다. 그 밖의 Kafka·Spark·ClickHouse 설정 변경은 별도로 정의한다. 그 밖의 제외 항목: 구간 사이 선형 전환, 프로파일 반복 실행, 시뮬레이션 시각을 이벤트 시각에 반영, `ops.producer_stats` 스키마 변경, Grafana 구간 annotation.

| 생성기 단독 | 약 44,000 EPS(파일 출력) | [로그 생성기](01-log-generator.md) 감사 후속 검증 |
| Kafka ACK | 5,000 EPS만 검증(1초 구간 ACK p95 최대 54ms) | [Kafka](02-kafka-ingestion.md) 완료 기준 3. 5,000 초과는 미검증 |

| 종단 간 지연 | 5,000 EPS에서 최대 9.87초, p99 7.72초 | [v1 목표 판정](overview.md#v1-목표-판정-2026-11-19) |

## 프로파일 정의

### 일간 프로파일 (`daily.csv`)

시뮬레이션 하루 24시간을 실제 60분으로 압축한다. 시뮬레이션 1시간 = 실제 150초다. 구간마다 EPS를 고정한다(계단식). 같은 EPS가 이어지는 시간은 한 구간으로 합친다.

| 시뮬레이션 시각 | 실제 시작(초) | 길이(초) | EPS | 구간 건수 | 의도 |
| --- | ---: | ---: | ---: | ---: | --- |
| 00–02 | 0 | 300 | 1,500 | 450,000 | 심야 |
| 02–06 | 300 | 600 | 800 | 480,000 | 최저점. 작은 배치의 지연·part 상태 |
| 06–08 | 900 | 300 | 2,000 | 600,000 | 출근 시간 |
| 08–10 | 1,200 | 300 | 3,500 | 1,050,000 | |
| 10–12 | 1,500 | 300 | 5,000 | 1,500,000 | v1 검증 기준 부하 |
| 12–13 | 1,800 | 150 | 7,000 | 1,050,000 | 점심 피크 |
| 13–18 | 1,950 | 750 | 5,000 | 3,750,000 | |
| 18–20 | 2,700 | 300 | 6,500 | 1,950,000 | |
| 20–22 | 3,000 | 300 | 8,000 | 2,400,000 | 하루 최대. Spark 입력 상한 대비 여유 20% |
| 22–23 | 3,300 | 150 | 4,000 | 600,000 | 피크 직후 감소 |
| 23–24 | 3,450 | 150 | 2,500 | 375,000 | |
| 합계 | | 3,600 | 평균 3,946 | 14,205,000 | |

- 피크/최저 비율은 10배다.
- 총 건수는 v1 60분 실행(17,835,801건)보다 적다. 저장 용량·TTL 검토는 추가하지 않는다.
- 최대 피크를 8,000 EPS로 둔 이유: 10,000 EPS 상한 아래에서 정상 상태 판정이 가능한 최대 부하를 보기 위해서다. 5,000 EPS에서 이미 최대 9.87초였으므로 이 구간에서 10초 초과가 예상된다. 그 결과가 조정 대상이다.

### 스파이크 프로파일 (`spike-12k.csv`)

- 파일명 변경(2026-11-19): 1차 측정 때는 `spike.csv`였다. `spike-10k.csv`를 추가하면서 spike EPS를 이름에 넣었다. 1차 측정 원자료 JSON의 `profile`은 당시 이름 그대로 둔다.

| 구간 | 실제 시작(초) | 길이(초) | EPS | 의도 |
| --- | ---: | ---: | ---: | --- |
| warmup | 0 | 300 | 5,000 | 안정화, 기준 지연 측정 |
| spike | 300 | 150 | 12,000 | 트리거당 입력 60,000건 > 상한 50,000건. 약 300,000건 누적 |
| recovery | 450 | 450 | 5,000 | backlog 해소 시간 측정 |

- 총 900초, 4,800,000건이다.
- 12,000 EPS는 Spark 이론상 최대치(트리거 5초 × 50,000건 = 10,000 EPS)를 일부러 넘긴 값이다. 누적은 처음부터 확정이다. 이 프로파일로 보는 것은 누적량과 회복 시간, 즉 backlog 처리 성능이다.
- 일간 프로파일과 분리한 이유: 스파이크는 상한 초과를 일부러 만드는 시험이라 일간 구간 판정을 오염시킨다. 피크 직후에 넣으면 backlog 원인을 구분할 수 없다. 세팅 비교를 15분 단위로 반복할 수 있다.
- 이론상 회복은 상한 여유분(10,000 − 5,000 EPS)으로 약 60초다. ClickHouse 적재 경로 포함 실제 값은 측정으로 정한다.
- 생성기 2개 프로세스 실행(2차 측정부터): `spike-12k-half.csv`(warmup 2,500 / spike 6,000 / recovery 2,500 EPS)를 생성기 2개로 동시에 실행한다. 근거와 판정 방식은 [상한 확인 프로파일](#상한-확인-프로파일-spike-10kcsv)의 2개 프로세스 실행과 같다.

### 상한 확인 프로파일 (`spike-10k.csv`)

| 구간 | 실제 시작(초) | 길이(초) | EPS | 의도 |
| --- | ---: | ---: | ---: | --- |
| warmup | 0 | 300 | 5,000 | 안정화, 기준 지연 측정 |
| ceiling | 300 | 150 | 10,000 | 트리거당 입력 50,000건 = 상한. 상한 속도를 지속 처리하는지 확인 |
| recovery | 450 | 450 | 5,000 | 누적이 생겼으면 해소 시간 측정 |

- 총 900초, 5,250,000건이다. 구간 길이는 스파이크 프로파일과 같아서 두 결과를 같은 시각축으로 비교할 수 있다.
- 스파이크 프로파일과 목적이 다르다. 스파이크는 상한을 넘겨 누적을 확정으로 만들고 backlog 처리 성능을 본다. 이 프로파일은 입력을 상한에 맞춰 Spark가 그 속도를 따라가는지 판정한다.
- 필요한 이유:
  - 스파이크 1차 측정에서 Spark 실처리량은 약 8,350 EPS였다. 이론상 최대치 10,000 EPS에 못 미쳤다. [자원 조정](#자원-조정)으로 Spark `cpus`를 3에서 4로 올렸으므로 그 효과를 판정할 입력이 필요하다.
  - 12,000 EPS는 생성기가 단일 스레드 한계로 내지 못했다(10,717 EPS). 10,000 EPS는 생성 기준을 충족할 가능성이 높아 처리 경로만 따로 판정할 수 있다.
- 예상 결과는 둘 중 하나다.
  - 배치를 5초 안에 처리하면 누적은 거의 없다. 이 경우 Spark가 이론상 최대치까지 처리한다고 판정한다.
  - 실처리량이 1차 측정값(8,350 EPS) 그대로면 (10,000 − 8,350) × 150초 ≈ 250,000건이 누적된다. 해소 속도는 약 3,350건/s, 회복은 약 75초로 추정한다.
- 생성기 2개 프로세스 실행(2차 측정부터): `spike-10k-half.csv`(warmup 2,500 / ceiling 5,000 / recovery 2,500 EPS)를 생성기 2개로 동시에 실행해 합계를 `spike-10k.csv`와 같게 맞춘다.
  - 근거: 1차 측정에서 단일 프로세스는 ceiling 평균 9,359 EPS(−6.4%)에 그쳤다. 그때 프로세스 CPU는 평균 0.91코어, 최대 1.04코어였다. Spark를 끄고 단독으로 10,000 EPS를 보내면 메인 스레드는 0.47코어만 쓴다. 호스트가 물리 4코어 × SMT 2(i7-1165G7)라서 전체 스택이 돌 때 같은 일에 CPU 시간이 약 2배 든다. 호스트 여유(ceiling 평균 사용 5.0코어 / 8)는 남아 있었으므로 프로세스를 나누면 각자 약 0.5코어로 목표를 낼 수 있다.
  - 생성기 코드는 바꾸지 않는다. 두 프로세스는 `run_id`가 다르다. 판정은 두 `run_id`의 1초 구간 합계로 한다. `event_id`는 UUID4라서 겹치지 않는다.

## 생성기 요구사항

### 설정

| 키 | `.env.example` 예시값 | 규칙 |
| --- | --- | --- |
| `PRODUCER_LOAD_PROFILE` | 빈 값 | 프로파일 CSV 경로. 빈 값이면 기존처럼 `PRODUCER_EPS` 고정 속도로 실행한다. 상대 경로는 프로젝트 루트 기준이다 |

- 키는 다른 `PRODUCER_*` 키처럼 반드시 명시한다. 빈 값을 허용하는 키로 추가한다.
- 프로파일을 지정하면 `PRODUCER_EPS`는 쓰지 않는다. 키 자체와 값 검증은 기존대로 유지한다.
- `PRODUCER_MAX_EVENTS`는 프로파일과 함께 적용한다. 프로파일 종료나 최대 건수 도달 중 먼저 오는 쪽에서 종료한다. 프로파일 측정은 `0`(무제한)으로 실행한다.
- 프로파일 파일 위치: `apps/log_generator/profiles/daily.csv`, `apps/log_generator/profiles/spike-12k.csv`, `apps/log_generator/profiles/spike-10k.csv`, `apps/log_generator/profiles/spike-12k-half.csv`·`apps/log_generator/profiles/spike-10k-half.csv`(2개 프로세스 동시 실행용).

### 프로파일 파일 형식

```csv
duration_sec,eps,label
300,1500,00-02
```

- 첫 줄은 헤더 `duration_sec,eps,label`로 고정한다.
- `duration_sec`·`eps`는 양의 정수, `label`은 빈 값이 아닌 문자열이다.
- 다음 경우 생성 시작 전에 설정 오류(종료 코드 2)로 종료한다: 파일 없음·읽기 실패, 헤더 불일치, 열 개수 불일치, 정수 변환 실패, 1 미만 값, 빈 `label`, 데이터 행 0개.

### 속도 제어

- 구간 안에서는 기존 속도 제어(5ms 틱, 누적 목표 대비 부족분 출력, 한 틱 허용량 2배 초과 밀림 포기)를 그대로 쓴다.
- 구간 전환 시 누적 기준을 현재 시각·현재 출력 건수로 다시 잡고 새 EPS와 한 틱 허용량을 적용한다. 이전 구간의 부족분을 새 구간에서 몰아서 보내지 않는다.
- 구간 경계는 실행 시작 시각(monotonic) + 누적 `duration_sec`로 정한다. 출력 지연으로 경계를 넘긴 만큼 다음 구간이 짧아지며, 전체 실행 길이는 프로파일 합계를 유지한다.
- 마지막 구간이 끝나면 flush 후 `completed`로 종료한다.

### 이벤트 시각

- `event_timestamp`는 기존처럼 실제 생성 시각(UTC)이다. 시뮬레이션 시각을 쓰면 종단 간 지연 측정이 깨지므로 반영하지 않는다.

### 상태·통계·운영 지표

- 주기 상태 줄에 현재 구간의 `target_eps`와 `label`을 추가한다.
- 최종 통계의 `target_eps`는 프로파일 실행이면 프로파일 이름(파일 경로)과 구간 목록(`label`·`duration_sec`·`eps`)으로 대신 기록한다.
- 구간 전환 시 stderr에 전환 시각·이전/다음 `label`·EPS를 JSON 한 줄로 기록한다.
- `ops.producer_stats.target_eps`에는 1초 구간 시작 시점의 구간 EPS를 기록한다. 스키마는 바꾸지 않는다. 경계를 걸친 1초 행은 판정에서 제외한다.
- 파이프라인 운영 대시보드의 기존 Producer 패널(`목표`·`생성`·`ACK`)이 `target_eps`를 그대로 그리므로 Grafana 변경은 없다.

## 측정 방법

- 자원·설정은 `.env`·Compose 기본값 그대로다. Kafka UI는 끈다. 측정 중 코드·설정을 바꾸지 않는다.
- Spark는 측정마다 별도 체크포인트·`latest`로 시작한다. 생성기는 Spark 첫 배치 진행 로그 확인 후 시작한다.
- 각 프로파일 실행의 생성기 `run_id`와 Spark `run_id`를 기록한다.
- 구간 지표는 `ops.producer_stats`·`ops.spark_query_progress`·`silver.order_events`에서 구간 시각으로 잘라 집계한다. 측정 스크립트·결과 JSON은 `docs/measurements/`에 둔다.
- 측정 중 Kafka·Spark·ClickHouse 컨테이너 CPU·메모리를 함께 기록한다.
- WSL VM 정지 구간이 발생하면 [호스트 멈춤 기록](04-clickhouse-storage.md#호스트-멈춤-기록)으로 확인하고, 해당 구간은 v1 판정과 같은 방식으로 분리해 보고한다.

## 판정 기준

### 일간 프로파일

실행 시작 후 120초는 워밍업으로 제외한다. 아래 기준을 구간별로 판정하고 표로 기록한다.

1. **생성·전송:** 구간 ACK EPS가 목표의 ±5% 이내. 1초 구간 ACK p95 100ms 이하.
2. **종단 간 지연:** `event_timestamp` → `ingested_at` p99 10초 이하, 10초 초과 건수 기록.
3. **Spark 처리:** 구간 내 트리거 시간이 5초 이하이고 Kafka → 콜백 p95가 구간 동안 증가 추세가 아님.
4. **건수 대조:** 실행 전체에서 생성 = ACK, 정상 주문 생성 건수 = `silver.order_events` 적재 건수(`event_id` 고유 수 포함).
5. **오류:** 쿼리·출력·ClickHouse 쓰기 실패 0건, Spark 재시작 0회.

기준을 못 넘긴 구간은 실패로 기록하고 원인 구간(생성기·Kafka·Spark·ClickHouse)을 [파이프라인 운영 대시보드](05-grafana-dashboard.md#파이프라인-운영-대시보드) 판정 순서로 지목한다. 실패 자체는 이 문서의 완료를 막지 않는다. 조정은 후속 작업이다.

### 스파이크 프로파일

1. **생성·전송:** spike 구간 ACK EPS가 12,000의 ±5% 이내. 2개 프로세스로 실행하면 두 `run_id`의 합계로 본다. 못 미치면 생성기·Kafka 한계로 기록하고 이후 기준은 참고값으로 본다.
2. **누적:** spike 구간에서 offset backlog가 0보다 커지고 최댓값을 기록한다.
3. **회복:** recovery 구간 안에 backlog가 0으로 돌아오고 Kafka → 콜백 p95가 warmup 구간 수준(warmup p95의 1.5배 이내)으로 돌아온다. 회복 시간(spike 종료 → 두 조건 충족)을 기록한다.
4. **건수 대조·오류:** 일간 프로파일 기준 4·5와 같다.

### 상한 확인 프로파일

1. **생성·전송:** ceiling 구간 ACK EPS가 10,000의 ±5% 이내. 2개 프로세스로 실행하면 두 `run_id`의 합계로 본다. 못 미치면 이후 기준은 참고값으로 본다.
2. **상한 처리:** ceiling 구간에서 입력 50,000건 배치의 트리거 시간이 5초 이하이다. 실처리량(50,000 ÷ 평균 트리거 시간)과 offset backlog 최댓값을 기록한다. 스파이크 1차 측정(8,350 EPS, 381,158건)과 비교한다.
3. **회복:** 누적이 생겼으면 스파이크 프로파일 기준 3과 같은 방식으로 회복 시간을 기록한다.
4. **자원:** 컨테이너별 CPU 상한에 걸린 주기 비율, 메모리 최대치, 생성기 프로세스 CPU를 기록한다. 스파이크 1차 측정의 Spark 16.8%와 비교한다. `memory.peak`는 컨테이너 안에서 초기화할 수 없고 페이지 캐시를 포함하므로, Spark는 측정 중 `memory.stat`의 `anon`·`file`을 함께 기록한다(2차 측정부터).
5. **건수 대조·오류:** 일간 프로파일 기준 4·5와 같다.

해석:

- **Spark 실효 처리량은 상한 10,000 EPS가 아니라 약 8,350 EPS다.** 입력 50,000건으로 꽉 찬 배치 41개의 트리거 시간이 평균 5,986ms(최대 9,942ms)였다. 5초 트리거보다 길어서 실효 처리량은 50,000 / 5.99초 ≈ 8,350 EPS다. 내역은 분류 평균 3,361ms, 정상 주문 쓰기 평균 2,246ms다. warmup 배치(약 25,000건)는 평균 3,066ms였다. 회복이 이론값 60초보다 긴 103초가 된 것도 이 때문이다(해소 속도 약 3,350건/s, 381,158 / 3,350 ≈ 114초).
- **일간 프로파일 피크 8,000 EPS는 이 실효 처리량에 거의 붙어 있다.** 일간 측정에서 20–22시 구간에 backlog가 누적될 가능성이 크다.
- **생성 미달 원인은 확정하지 못했다.** 같은 날 Spark를 끈 36초 실행에서는 12,000 EPS(평균 11,957, ACK p95 최대 94.8ms)를 유지했다. 전체 스택에서는 ACK 지연이 100~400ms로 자주 올랐고, 경과 434·439~442초에는 ACK 0건 뒤 p95 4,558ms가 나왔다. 생성 루프는 밀린 분량을 포기하므로 ACK 지연·큐 증가 구간에 생성 EPS가 떨어졌다. 후보는 생성기·Kafka의 CPU 경합이다. WSL 부하 평균(load1)은 warmup 3.93 → spike 5.01(최대 6.55)이었다. 생성기 프로세스·컨테이너별 CPU는 기록하지 않았다.
- 경과 413.6초에 WSL 멈춤 2,128ms가 `ops.host_stalls`에 기록됐다(load1 5.81). 같은 시각 1초 구간 생성이 4,332건으로 떨어졌다. 이 구간을 빼도 기준 1 미달은 바뀌지 않는다.
