# Spark 배치 지연 급증 원인 진단 (60분)

- 상태: 측정 완료(원인 일부 확정)
- 적용 범위: 제품 v1, 로컬 WSL2 + Docker Desktop 환경의 Spark Structured Streaming(4단계 구성)
- 실행 시각: 2026-11-18 16:21:25~17:21:25 UTC(2026-11-19 01:21~02:21 KST)
- 코드·설정 변경: 없음. 진단용 JVM 옵션만 별도 컨테이너에 추가했다.
- 원본 로그: 세션 임시 디렉터리(scratchpad)의 `diag2-*.log`, `gc2.log`. 저장소에는 보관하지 않는다.

## 배경

이전 측정에서 분류 시간(`classification_ms`, 단조 시계)이 4초를 넘는 배치가 7회 실행 중 13회 나왔다. 예: 08:27 UTC 배치 234, 트리거 9.4초. 그때 배제한 후보는 다음과 같다.

- Grafana: 없는 실행에서도 발생했다.
- ClickHouse 부하: 급증 구간의 쿼리 CPU가 평소보다 낮았다.
- 레코드 내용: 보존된 6,143,878건을 건당으로 재분류했다. 평균 56µs였고 50ms를 넘는 건은 0건이었다.
- 메모리 압박: 이전 20분 진단 실행의 최대 사용량은 908MiB/3GiB였다.

이전 20분·25분 실행에서는 급증이 재현되지 않았다. 그래서 급증 순간을 잡으려고 관측 도구를 함께 켜고 60분 동안 실행했다.

## 방법

- Spark: 측정용 별도 컨테이너 `spark-diag2-20261119`로 실행했다. 체크포인트는 `/opt/spark/checkpoints/diag2-20261119/ckpt`, `SPARK_STARTING_OFFSETS=latest`, 그 밖의 설정은 `.env` 기본값(`local[3]`, driver 2g, 트리거 5초)이다.
  - 이벤트 로그: `spark.eventLog.enabled=true`
  - GC·safepoint 로그: `-Xlog:gc*,safepoint:file=.../gc.log:time,uptime`
- 생성기: WSL Ubuntu에서 `PRODUCER_OUTPUT=kafka`로 약 5,000 EPS, 3,600초 실행했다. 상태 로그는 1초 간격이다.
- 프로세스 추적: 호스트에서 1초마다 `docker exec`로 컨테이너 안 python 프로세스의 생성·종료를 기록했다.
- 자원: 호스트에서 약 3~5초마다 `docker stats`로 Spark·Kafka·ClickHouse의 CPU·메모리를 기록했다.
- 지표: `ops.spark_batch_attempts`, `ops.spark_query_progress`(run_id `98099b5d-2d3d-4a41-8478-66770cc467a5`)

생성기, 프로세스 추적, `docker stats`는 서로 독립된 시계열이다. 셋이 같은 시각에 함께 끊기면 Spark 내부가 아니라 VM 전체가 멈춘 것으로 판정한다.

### 동시 정지: 16:50:33~16:50:48 UTC

| 관측 대상(위치) | 정지 구간 | 근거 |
| --- | --- | --- |
| Spark JVM GC 로그(컨테이너) | 16:50:33 → 16:50:48, 약 15초 | 초당 약 20줄이던 로그가 0줄이 됐다 |
| 생성기 상태 로그(WSL 배포판) | 16:50:33 → 다음 출력까지 8.8초, 이어 4.2초·2.7초 간격 | 구간 처리량이 12~208 EPS로 떨어졌고, 큐가 701~764건까지 쌓였다 |
| 프로세스 추적 `docker exec`(호스트) | 16:50:34 → 16:50:50, 16초 | 1초 간격 기록이 끊겼다 |
| `docker stats`(호스트) | 16:50:37 → 16:50:53, 16초 | 3~5초 간격 기록이 끊겼다 |

- 생성기는 WSL Ubuntu 배포판에서, Spark는 Docker Desktop 컨테이너에서 돈다. 둘은 같은 WSL2 유틸리티 VM을 쓴다. 서로 무관한 프로세스가 같은 15초 동안 함께 멈췄으므로 **VM 전체 정지**로 판정한다.
- 이번 정지는 시계 점프가 아니다. GC 로그의 JVM 가동 시간(단조 시계)과 벽시계 차이에 0.5초를 넘는 변화가 없었다. 15초는 실제로 흘렀다.
- 정지 시각 전후의 게스트 커널 로그(`dmesg`)에는 메시지가 없었다. hung task, soft lockup, OOM 모두 없었다. 다만 soft lockup(약 20초)·RCU stall(약 21초) 경고 기준이 정지 길이(15초)보다 길어, 이 부재는 원인 판별 근거가 되지 않는다(2026-11-26 정정).
- 게스트 CPU 포화는 원인으로 보기 어렵다. 포화는 프로세스를 느리게 할 뿐 모두 멈추지 않으며, 컨테이너 `cpus` throttle은 WSL 생성기까지 함께 멈추지 못한다. 서로 다른 위치의 프로세스가 모두 0 출력이었으므로 Windows 호스트가 VM의 vCPU를 스케줄하지 않은 것으로 추정한다. 호스트 CPU 사용률은 기록하지 않아 호스트 CPU 포화 여부는 판별하지 못했다.
- 정지 전후 Spark 컨테이너 메모리는 2.34GiB/3GiB로 안정적이었다. 컨테이너 OOM 신호는 없었다.
- 배치 350 무렵(16:51:18 → 16:51:27)에도 프로세스 추적이 9초 끊겼다. 생성기 상태 로그에는 2.5초를 넘는 공백이 없어 VM 전체 정지인지는 확정하지 못했다.

### 부차 요인: 주기적 Full GC

| 시각(UTC) | GC | 시간 |

| 16:50:57.558 | `Pause Full (System.gc()) 728M->128M(444M)` | 2,025 ms |

- 두 Full GC는 정확히 30분 간격이다. Spark ContextCleaner의 주기적 GC(`spark.cleaner.periodicGC.interval`, 기본 30분)로 추정한다. 설정값은 확인하지 않았다.
- 배치 346(트리거 7.1초)은 VM 정지 직후 이 Full GC와 겹쳤다.
- 이전 20분 진단 실행에서 같은 종류의 Full GC는 214ms였다. 이번 2초는 정지 직후라 길어졌을 가능성이 있으나 확인하지 못했다.
- 이 밖에 100ms를 넘은 GC 정지는 Young GC 2회(124ms, 211ms)뿐이다.

## 판정

- 이번 실행의 최대 지연(배치 345, 트리거 18.0초)의 원인은 **WSL2 VM 전체 정지(약 15초)**다. Spark 코드, Python 분류 UDF, ClickHouse, Kafka 문제가 아니다.
- 부차 요인은 30분 주기 `System.gc()` Full GC(1.1~2.0초)다. Spark 쪽에서 조정할 수 있는 유일한 후보다.
- 이전 실행들의 급증 13회가 모두 같은 원인인지는 확인하지 못했다. 당시에는 동시 관측 도구가 없었다.

  - 2026-11-26 Windows 이벤트 로그 확인(정지 시각 2026-11-19 01:50:33~01:50:48 KST 전후, `Get-WinEvent`):
    - System(01:15~02:30): 3건, 모두 02:00 이후(BITS 시작 유형 변경, Volsnap 36). 정지 시각 전후 `Kernel-Power`(절전), `Resource-Exhaustion-Detector`(메모리 부족), Windows Update 기록 없음. 로그 보존은 2026-08-04부터라 기간 밖 삭제는 아니다.
    - Application(01:40~02:00): `igccservice` PowerEvent(01:49:02 다음 01:59:32)와 AppModel-State만 있음. 같은 간격의 공백이 다른 시간대에도 있어 원인 근거로 보지 않는다.

    - 판정: 호스트 이벤트 로그에서 정지 원인 기록을 찾지 못했다. 다음 측정에서는 `logman` 성능 카운터(가용 메모리, Pages/sec, CPU, Hypervisor 논리 프로세서 실행률)를 1초 간격으로 함께 수집한다.
